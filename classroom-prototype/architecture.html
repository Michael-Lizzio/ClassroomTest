How Chalkroom would run on Supabase

Ten topics, in plain language. The prototype is static and fakes everything live. This page is the plan for the real thing. Prices and plan limits change, so every number here is a planning estimate to check before you commit.

1Stack and why

Recommendation: Expo (React Native) with React Native Web, one TypeScript codebase for iOS, Android and the web, with Supabase as the backend.

  • Why Expo. One codebase ships to both app stores and the web. Native camera access makes QR scanning reliable. EAS Build and EAS Update handle store builds and fast fixes.
  • Trade-off. Board drawing and handwriting need care on low-end Android. Use a native canvas module (for example react-native-skia) for ink and keep text layout simple.
  • Alternative: a web app wrapped with Capacitor. Fastest route, and the prototype's code carries over. Weaker on drawing performance and on store reviewer expectations for a live-classroom app. Choose it only if the MVP is web-first.
  • Backend. Supabase for Auth, Postgres, Realtime, Storage and Edge Functions. Everything sits behind Row Level Security, so the client can't read data it shouldn't.

3Realtime design

One Realtime channel per class session, named class:<session_id>. Each message type goes over the mechanism that fits it.

MechanismWhat goes over itWhy
BroadcastBoard writing deltas, teacher pointer position, live caption text, area visibility changesShort-lived and high-rate. Nothing needs to be stored.
PresenceWho is online, their role, display name, when they joinedBuilt for "who is here" state. Drops automatically on disconnect.
Postgres ChangesQuestions, lesson notes, board items, final transcript segmentsMust survive a refresh and be queryable. Listeners get rows that RLS allows them to see.

Example payloads.

// Broadcast "board.write": one batch of pen or text deltas, every 100–150 ms
{ "type": "board.write", "seq": 1841, "sender": "teacher",
  "ops": [ { "id": "b_203", "kind": "text", "x": 30, "y": 112, "chars": "6CO" } ] }

// Broadcast "caption.partial" and "caption.final"
{ "type": "caption.final", "seq": 1844, "t_ms": 58210, "text": "The light reactions happen in the thylakoid." }

// Broadcast "areas.visibility": the teacher toggles an area
{ "type": "areas.visibility", "seq": 1850, "mode": "grid", "hidden": ["br"] }

// Presence "student" state
{ "role": "student", "display_name": "Priya", "joined_at": "2026-11-07T09:41:03Z" }

// Postgres change: a new row in questions (only the teacher's subscription sees all of them)
{ "table": "questions", "event": "INSERT",
  "new": { "id": "q_881", "session_id": "s_12", "student_id": "u_77", "text": "…", "snapshot_path": "snap/q_881.svg" } }
  • Ordering. Each sender numbers messages with seq. Clients apply Broadcast ops in order per sender and drop duplicates. Board truth comes from Postgres, not from message order.
  • Reconnecting. Exponential backoff with jitter (0.5 s, doubling, capped at 15 s). On rejoin, reload the board snapshot, then resume from the last seq seen.
  • Late joiners. A student who joins mid-class calls one RPC that returns current board items, visible areas, the latest slide and the last 60 seconds of captions. Then they subscribe.
  • Throttling and batching. Pointer position at 10–20 Hz at most. Text is sent as 100–150 ms chunks, not per key press. Keep each message under 4 KB.
  • Limits. Check the current Realtime message-rate and payload limits for your plan in the Supabase docs before the load test. Budget with a safety margin of 2× the design rate.

4Data model

TableKey columnsNotes
classesid, teacher_id, name, school_idA teacher's recurring class.

Row Level Security (summary).

  • Students see only visible areas. board_items is readable by a student only when its area_id is visible, or it has no area.
  • Only the teacher sees all questions. A questions row is readable by the session's teacher.
  • Students see only their own questions. Readable when participant_id matches the caller's participant.
  • Notes are teacher-only until pushed_at is set, then they're readable as board items.
  • Anonymous students can't read any classes or notes rows, and can't write to sessions.

5Joining

  • Join codes. Eight characters from an alphabet without look-alikes (no 0/O, 1/I/L). Unique per active session, generated server-side.
  • Expiry. A code expires at the scheduled end of the session plus two hours, and can be rotated mid-class by the teacher. A teacher can also lock the room, so new joins are refused.
  • QR deep links. The QR encodes https://chalkroom.app/j/<code>. With universal links (iOS, apple-app-site-association) and app links (Android, assetlinks.json) the app opens directly. Otherwise the same URL serves the web join page.
  • Anonymous sign-in for students. The Edge Function join validates the code, calls anonymous sign-in, and creates a participants row with the display name. No email, no password.
  • Display names. Teacher-moderated, 20 characters, no duplicates within a class.

6Live transcription

  • Deepgram. Streaming, low latency, priced per minute of audio. A good default to test first. Confirm current rates.
  • AssemblyAI. Streaming with a strong accuracy record and easy speaker and language options. Per-hour pricing. Slightly higher per-minute cost than Deepgram for basic English. Confirm current rates.
  • Google Cloud Speech-to-Text. Broadest language coverage and tight integration if you're already on Google Cloud. Typically the highest per-minute list price. Confirm current rates.
  • Cost sanity check. A 45-minute class is 45 billed minutes of streaming. At roughly half a cent per minute, that's about 25 cents per class. Verify before budgeting.
  • Storage. Final text only, by default. Raw audio is never stored. Teachers can opt in to keep audio for a fixed period, and transcripts follow the retention rule in topic 9.

7Hosting and deployment

  • Web app. Static build on Cloudflare Pages or Vercel, served from the CDN. Preview deploys per pull request.
  • Supabase plan. Pro from the first pilot. The free plan pauses inactive projects and has lower Realtime connection limits, which a live classroom will hit quickly.
  • Edge Functions are enough for join, token minting, webhooks and moderation hooks.
  • A small separate server (Node WebSocket service or a worker on Fly.io, Render or Railway) is needed only when one of these happens: a speech provider needs a server-side relay, per-class server state outgrows Edge Function limits, or you need long-lived connections that Edge Functions don't support well. Plan for it around month three.
  • Environments. Three Supabase projects: dev, staging, prod. Migrations via the Supabase CLI, checked in and applied by CI. Seed data for dev only.
  • CI. GitHub Actions: type-check, lint, unit tests, a Realtime smoke test against staging, then deploy.
  • App store builds. EAS Build for iOS and Android, TestFlight and Play internal testing for each release, EAS Update for JavaScript-only fixes. Expect store review to ask about child safety and data collection.

8Scale, cost and limits

LoadOne class of 301,000 classes at once
Realtime connections31 (one per device)About 31,000 concurrent. This is the first thing that breaks.
Broadcast messagesPeaks of 20–50 per second while writing, averaging a few per secondTens of thousands per second at peak. Batching is essential.
Database writesA few questions, board items and transcript batches per minuteSeveral thousand writes per minute. Fine for Postgres with indexes and batching.
Speech-to-text streams1 stream for 45 minutes1,000 concurrent streams. Provider concurrency limits and cost dominate.
StorageSnapshots of about 30 KB eachManageable. Delete snapshots with the session after the retention window.

What breaks first, in order: (1) Realtime concurrent connections and plan limits, so buy the add-on early. (2) Postgres Changes fan-out, because RLS is checked per subscriber, so move high-rate events to Broadcast. (3) Speech-to-text concurrency and spend, so cap streams per school. Costs at this scale are dominated by Realtime connections and transcription, not by Postgres. Use the provider's pricing page and the Supabase pricing page for real numbers.

9Security and privacy

Students may be minors, so privacy is a launch requirement, not a later task.

  • COPPA (under 13, US). Collect as little as possible from students. Use anonymous auth and display names only, with no email or persistent identifier shared with third parties. Use schools as the consent route where the school authorises the service, and get verifiable parental consent for direct-to-consumer use. Get a children's privacy review before any marketing to families.
  • FERPA (US, education records). Schools that receive federal funds can share student records with vendors that act as "school officials" under a data-use agreement. Under that agreement you may use the data only to provide the service, may not sell it or use it for ads, and must delete it on request.
  • Data retention. Default: transcripts and questions kept for one school year, then deleted. Snapshots deleted with the session. Schools can set shorter periods. Account deletion removes all personal data within 30 days.
  • Moderation of student questions. Only the teacher sees questions. Add a simple text filter on arrival, a report button, rate limits per student, and an admin audit log. Students never see each other's questions or names outside the class roster.
  • Security basics. Row Level Security tested in CI for every table (a test user can't read another student's rows). Edge Function secrets in Supabase vault. Signed URLs for snapshots, expiring in minutes. No PII in logs.

10Build plan

  1. Phase 0 · Prototype (done). This static demo. Used for founder reviews and teacher interviews.
  2. Phase 1 · MVP (about 8 weeks). Anonymous join by code and QR, teacher whiteboard with typed text, board areas with visibility, questions inbox with snapshots, roster and presence. One pilot school, web first.
  3. Phase 2 · Present and captions (about 6 weeks). Lesson notes synced to the board, Present mode, live captions with a streaming provider, transcript storage.
  4. Phase 3 · v1 (about 8 weeks). iOS and Android builds, school accounts and admin, COPPA and FERPA paperwork, retention controls, store launch.
